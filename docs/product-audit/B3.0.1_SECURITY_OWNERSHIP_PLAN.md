# B3.0.1 — Security & ownership hardening: implementation plan

> Checkpoint inserted by the owner before the coach UI rebuild (B3.1).
> **Status (2026-10-17): implemented and verified; awaiting owner review (uncommitted).** Results, changed contracts, test evidence and remaining risks: `B3_IMPLEMENTATION_LOG.md` (B3.0.1 section). Refinements made while coding (F5 first-day freezes, the exact early-unfreeze formula, gap narrowing by later back-dated terms) are recorded there and in the decision doc §0.
> Owner decisions it implements: O-15 (fix B3-S01, S03, S05), O-16 (private notes are author-private; an ended coach keeps no workspace access), O-17 (suspended accounts may read but not write messages), O-18 (server-side client read-only enforcement), **R-4 = Option C** (per-coach conversations, §9), **R-6 = date-based enforcement with safeguards** (§6.2), **B3-S07 = E2 + F-C** (rules in `B3_SUBSCRIPTION_EXTEND_FREEZE_DECISION.md` §0), and the defaults in §8.
> Every rule below is enforced **on the server**. UI changes are limited to what a stricter API response forces (noted per item).

## 0. Baseline facts (verified in code, 2026-10-15)

- **Client data procedures already require an active relationship and an active coach account.** `isAssignedCoachOf` (`api/client/_lib/access.ts`) checks `role === 'coach'`, `accountStatus === 'active'` and the `${coachId}__${clientId}` relationship with `status === 'active'`. This gates plans, logs, notes, check-ins, measurements, assessment, photos and plan versions. **An ended or transferred-away coach already cannot open the client's workspace data.** The remaining leaks are the five paths below.
- Relationship docs live in `coachClients`. `_id` is `${coachId}__${clientId}`. `status` is `active | ended`, with `pending` defined but never written; `endReason` is `released | transferred | unassigned`.
- Accounts: `accountStatus` is `active | pending | suspended | disabled`. A non-active session sees `AccountPending` / `AccountSuspended` instead of the app (`src/App.tsx`), so a suspended user has no messaging UI. Enforcement must still be server-side.
- Media uploads already require an active account (`api/media/_lib/policy.ts:116`).

## 1. B3-S01 — Relationship records leak across coaches (+ S01b, profile lookup)

### 1a. `coachClients.list({ clientId })`

**Current contract.** `authedProcedure`. With `clientId`, it returns **every** relationship doc for that client (any coach, any status, full fields: `subscription`, `subscriptionHistory`, prices, `inviteCode`, end fields, `mode`). It allows the client themself, `users.read`, or **any coach who has any relationship doc with the client, in any status**.

**Consumers.**

| Consumer | Uses | Needs |
|---|---|---|
| `CoachTimeline` → coach workspace History tab (`CoachClientHistory`) | every relationship: coach, dates, end reason, transfer mode | other coaches' **names and dates only** |
| `CoachTimeline` → `AdminClientDetail` | the same, for admins | full (admin has `users.read`) |
| `AddExistingClient` → `getClientAssignment(clientId)` | whether the found client is already the caller's active client | the caller's **own** docs |
| `getCoachDashboard` | uses the `coachId` branch, not `clientId` | unaffected |

**New rule.**

| Caller | Gets |
|---|---|
| The client themself | all their relationship docs, full (unchanged) |
| Admin with `users.read` | all, full (unchanged) |
| Coach with an **active** relationship with the client | own docs full; **other coaches' docs redacted** to the timeline fields `{_id, coachId, clientId, status, createdAt, endedAt, endReason, mode}` — no subscription, history, price, invite code or notes |
| Coach whose relationship **ended** (released / transferred away) | **own docs only**, full: their own business record. No other coach's doc, redacted or not |
| Coach with no relationship | `FORBIDDEN` (unchanged) |

### 1b. `adminUsers.get({ id })` (S01b, new in this checkpoint)

**Current contract.** Returns the full profile (email, phone, WhatsApp, Instagram, flags, invite code…) when the caller is self, holds `users.read`, or has **any relationship doc in either direction, any status**. Everyone else gets a redacted name card.

**Leak.** An ended coach keeps the client's contact details forever, and a former client keeps the former coach's. This contradicts O-16 ("the previous coach must not automatically retain access").

**New rule.** Full profile only for self, `users.read`, or an **active** relationship in either direction. Everyone else, ended relationships included, gets the existing redacted name card (it still has `displayName` and `photoUrl`, so the History timeline keeps naming previous coaches).

**Consumers checked.**
- Coach workspace header (`useCoachClientHeader`): active relationship, so unchanged.
- Client `fetchMyCoach`: active, so unchanged.
- `CoachTimeline` and `IncomingTransferRequests`: only need the name, which the redacted card has.
- `AdminClientDetail`: has `users.read`, so unchanged.

### Matrix (1a + 1b)

| Relationship of caller to client | 1a list | 1b profile |
|---|---|---|
| Active coach | own full + others redacted | full |
| Ended (released) coach | own only | redacted card |
| Transferred-away coach (`keep_plans` / `fresh_start`) | own only | redacted card |
| Suspended coach with an active relationship | own full + others redacted (roster reads stay allowed for suspended coaches today; see risk R-3) | full |
| Unrelated coach | `FORBIDDEN` | redacted card |
| Client (self) | all, full | self: full; own active coach: full; former coach: redacted |
| Admin `users.read` | all, full | full |

**Tests (api, `coachClients.test.ts` + `certification.test.ts`):**
- `list({clientId})` matrix above.
- The redacted shape contains no `subscription`, `subscriptionHistory`, `price` or `inviteCode`.
- An ended coach receives no other coach's doc.
- `adminUsers.get` matrix above.
- No email or phone in redacted results.

**Regression:**
- e2e 20 (History shows "Coach Pro"), 21 (transfer), 61 (Add Existing names no coach).
- Admin client detail.
- Unit tests for `getClientAssignment`.

**Compatibility.** Additive restriction; response shapes are unchanged (the redacted docs keep the document shape with fields omitted). Old clients (RC2 in production) only use these paths for the same screens. No migration.

## 2. B3-S02 — Notes are author-private (+ the assessment private note)

### 2a. `coachNotes` (`api/_trpc/routers/clientCoachNotes.ts`)

**Current contract.**
- `list` returns **all** notes for the client to any reader allowed by `canReadClientData` (the active coach or `clients.readAll`), or only `visibility: 'client'` notes to the client. The limit is 50.
- `update` and `delete` require `canWriteCoachOwned` and have **no author check**.
- `create` stores `authorId` and `authorRole`.

**Consumers.**
- Workspace Notes tab (`CoachClientNotes`): list, create.
- Workspace Overview (latest three).
- View-as-client anchored notes (`EntityNotes` via `ClientNotesProvider`).
- The client's Coach › Updates and inline notes, which only receive shared notes.
- `update` and `delete` have no UI caller today.

**New rule.**

| Reader | `list` returns |
|---|---|
| Client | `visibility: 'client'` notes (unchanged) |
| Active coach | shared notes (`visibility: 'client'`, any author — the client sees them anyway) **plus private notes whose author is the caller** |
| Admin `clients.readAll` | all notes (oversight). **Audited** whenever the result contains another author's private note (R-1) |
| Ended / transferred-away coach | `FORBIDDEN` (already, via `canReadClientData`) |

**`update` / `delete`:** only the note's author, or an admin with `clients.writeAll`. Any other caller gets **`NOT_FOUND`**, not `FORBIDDEN`, so a probe cannot confirm that a private note exists.

**Legacy notes without `authorId`:**
- The note's author is taken to be the coach whose relationship stint covered the note's `createdAt` (from the relationship docs' `createdAt` / `endedAt`).
- If no stint matches, the note is visible to admins only.
- This is decided at read time; there is no data migration.

### 2b. Assessment private note (`clientProfiles.privateNotes`)

**Current contract.**
- One string per client, `privateNotes.assessment`, plus `updatedBy` and `updatedAt` (`setCoachNotes`).
- The legacy `assessment.coachNotes` is migrated into it on submit.
- Every coach or admin reader gets it back as `coachNotes`.

**Leak.** After a transfer the new coach reads the previous coach's note. The first `setCoachNotes` by the new coach **overwrites** it, destroying the previous coach's record.

**New rule.**

| Aspect | Rule |
|---|---|
| Storage (additive) | `privateNotes.assessmentByAuthor.<authorId> = { text, updatedAt }` |
| Read | a coach gets **their own** entry as `coachNotes`. The response shape is unchanged |
| Write | writes only the caller's entry. Nobody else's note is overwritten |
| Legacy single field, with `updatedBy` | treated as authored by `updatedBy`. Migrated into that author's entry the first time that author writes |
| Legacy single field, without `updatedBy` | visible to a coach only if the client has never had another coach (every relationship doc is the caller's). Otherwise admin-only. Never deleted |
| Admin `clients.readAll` | gets the current active coach's entry (else the legacy note). The admin API shape is unchanged (one string). **Audited** when a note is returned (R-1) |

**Tests (api, `notePrivacy.test.ts` extended).** Coach A writes a private note and a shared note, then the client is transferred to coach B (`keep_plans`), then:
- B's list contains A's shared note but **not** A's private note;
- B's `update` / `delete` of either of A's notes returns `NOT_FOUND`;
- A's list returns `FORBIDDEN`;
- the client still sees only shared notes;
- an admin sees all notes.

The assessment note follows the same pattern:
- A writes, the client is transferred, then B reads an empty note;
- B writes, then A's entry is intact (checked through the admin and through the data);
- each legacy branch (with and without `updatedBy`) is covered.

Regression: e2e 61 (private note never reaches the client), workspace Notes unit test, `CoachClientAssessment`.

**Compatibility and migration.**
- Read-time rules plus one additive field. No rewrite of existing documents.
- Existing private notes stay readable by their author, and admins keep oversight.
- **Visible behaviour change:** after a transfer, the new coach no longer sees the previous coach's private notes.

## 3. B3-S03 — Public invite lookup returns personal data

**Current contract.** `invites.getByCode` is a `publicProcedure`. It returns the **whole invite doc**: the invitee's email, phone and name, the coach id and name, and the subscription template (price, currency, plan, months, trial days), plus who created it and claim fields. There is no rate limit.

**Consumer.** `AcceptInvite.tsx` (public claim screen) reads:

| Field | Used for |
|---|---|
| `status`, `expiresAt` | claimability |
| `coachName` | the "from coach" line |
| `displayName`, `email`, `phone` | pre-filling the form |
| `code` | the claim call |

`claim` **already takes the email from the server-side invite** when it has one (`inv.email || input.email`), so the client never needs the real email.

**New rule.**
- `getByCode` returns only `{ code, status, claimable, expiresAt, coachName, displayName, hasEmail, emailHint }`.
  - `emailHint` is masked, e.g. `m•••@gmail.com`.
  - No phone, no price or subscription template, no coach id, no creator, no claim fields.
- Per-IP rate limit on `getByCode` (30 per 10 min) and `claim` (10 per 10 min), using the existing `enforceRateLimit` + `getClientIp` (as `auth.ts` does).
- Unknown code → `NOT_FOUND` (unchanged; no detail).

**Required UI change (functional, not visual):**
- The claim form shows the masked email as read-only text when the invite carries one.
- The phone field starts empty; the claimant types it (it is required by `claim`).
- No change to the public auth visuals.

**Tests (api, `coachClients.test.ts` invites block + `certification.test.ts`):**
- The response has no `email`, `phone`, price or `coachId`.
- The masked hint has the right format.
- The rate limit returns `TOO_MANY_REQUESTS`.
- `claim` works with an emailed invite (no email input) and with a no-email invite (email input).

Regression: e2e 10 (invite interstitial), 20 (invite generate), any claim flow.

**Compatibility.** An old client (RC2) reading `inv.email` / `inv.phone` would simply not pre-fill. The claim still succeeds because the server uses the invite's email.

## 4. B3-S04 — Suspended accounts: read-only messaging (O-17)

**Current contract.**
- Every message procedure is `authedProcedure`, so any account status is accepted.
- `authorizeThreadAccess` allows: the client themself (any status); an admin with `clients.writeAll`; a coach with an **active relationship** (the coach's own account status is not checked).

**New rule.**

| Procedure | Rule |
|---|---|
| `list`, `coachThreadsSummary`, `markRead` | allowed for any reader `authorizeThreadAccess` admits, within the conversation-ownership rules of §9. `markRead` only records a read receipt |
| `send`, `edit`, `delete`, `react` | **require the caller's `accountStatus === 'active'`** (coach, client and admin alike), on top of thread access. Otherwise `FORBIDDEN` with `data.reason: 'ACCOUNT_NOT_ACTIVE'` and no other detail |
| Attachments (`/api/media`, category `message`) | already require an active account. Unchanged and covered by a test |
| Broadcast | a fan-out of `send`, so covered |

Which statuses count:
- "Suspended" here means any status other than `active` (`suspended`, `disabled`, `pending`).
- Pending accounts cannot reach the app today anyway.

**Consumers.** Coach inbox and thread, client chat, broadcast, outbox delivery.
- A send that was queued **before** the suspension now fails permanently with that reason. The outbox already shows permanent failures with Discard, so nothing is lost silently.
- No UI change: suspended users see the suspended screen.

**Tests (api, `messages.test.ts`):**
- A suspended coach with an active relationship can `list` / `markRead` but gets `FORBIDDEN` on `send` / `edit` / `delete` / `react`.
- The same for a suspended client.
- Active accounts are unaffected.
- A media upload by a suspended account is refused.
- `outboxIdempotency` stays green.

Regression: e2e 31, 32, 33, 60.

**Compatibility.** A pure restriction for non-active accounts. No data change.

## 5. B3-S05 — Ended relationship's subscription is still editable

**Current contract.** `coachClients.updateSubscription` (`protectedProcedure`) allows the owning coach (by id prefix) or an admin with `clients.writeAll`. `updateSubscription()` loads the doc **without checking its status**. `end` already refuses a non-active relationship.

**Consumer.** Only the coach workspace subscription panel (`CoachSubscriptionPanel` via `CoachClientSubscriptionTab`). It is reachable only for active clients; the workspace data needs an active relationship.

**New rule.**
- The owning coach may change a subscription only while the relationship is **active**. Otherwise `CONFLICT`, "This client is no longer yours".
- Admins with `clients.writeAll` keep the ability to correct an ended relationship's record (decision R-2). The subscription service writes no audit entry today; B3.0.1 **adds** an audit entry for admin corrections.

**Tests (api, `coachClients.test.ts`):**
- A former coach's `setTerm` / `extend` / `freeze` on an ended relationship returns `CONFLICT`.
- The active coach is unaffected.
- An admin correction on an ended relationship succeeds and writes the new audit entry.
- `subscriptionHistory` stays green.

**Compatibility.** A restriction with no data change.

## 6. B3-S06 — Server-side client subscription read-only (O-18)

### 6.1 Verified scope (what "read-only" means today)

`src/lib/subscription.ts` and `src/stores/subscriptionGate.ts`, plus the screens that read them:
- **Effective status:**
  - `frozen` while `now < frozenUntil`;
  - `expired` once `now ≥ endAt`;
  - stored `cancelled` / `ended` / `expired` win.
- **Access:**
  - `full` for trial / active;
  - `readonly` for expired / cancelled / frozen / ended;
  - `limited` for pending / none.
- **Read-only blocks only coach-plan logging:**
  - nutrition log edits (every `nutritionStore` mutation);
  - starting a workout (`workoutStore`);
  - cardio start / log (Cardio screen);
  - the Today "+ water" (part of the nutrition log).
- **Not blocked when read-only:**
  - weight logs, measurements, progress photos;
  - check-in submit, messages, the assessment;
  - freeze requests, settings, reminders, daily checklists.
- `limited` hides the plan screens entirely (`SubscriptionGate`). It is **not** part of read-only.

The only server path for those logs is **`sync.push`** (collections `workoutLogs`, `nutritionLogs`, `cardioLogs`); the `logs*` routers are read-only.

### 6.2 Approved server rule (owner, R-6: date-based, with safeguards)

**Scope.** `sync.push` for `workoutLogs`, `nutritionLogs` and `cardioLogs` only. Every other collection, deletions, pulls, singletons and coach writes are unchanged, and so are the B0 / B1 / B2 sync guarantees (revision CAS, per-record contract rejection, rejected records kept on the device).

**The activity date.** The record's own day (`YYYY-MM-DD`): the record id for the day-keyed workout and nutrition logs, `data.date` for cardio. The sync arrival time is never used. A cardio record without a `date` is not judged (accepted, as today).

**Authorized vs unauthorized time.** Logging is unauthorized only while the client **had a coach** and that coach's subscription was **read-only** (lapsed, cancelled, ended or inside a freeze). Time with no coach is the free tracker (full access in the app) and time with a `pending` / no subscription is `limited` in the app (UI-only, as today) — neither is enforced. The server derives, for every relationship of the client and **only where the stored data proves it**, these unauthorized windows (each clipped to the relationship's lifetime `[createdAt, endedAt)`):

| # | Window | Source (reliable) |
|---|---|---|
| U1 | After the current term ended: `[endAt, …)` — for cancelled terms from `min(endAt, cancelledAt)` | `subscription` (latest term; nothing later exists) |
| U2 | Inside a B3.0.1 freeze: `[frozenFrom, frozenUntil)` | `subscription` with `freezeCredit` |
| U3 | Past B3.0.1 freezes, ended early or not: `[frozenFrom, actual end)` | `subscriptionEvents` |
| U4 | Renewal gap: a term that lapsed before it was renewed, from its end until the renewal — or until the new term's start if the coach back-dated it: `[h.endAt, min(h.endedAt, next.startAt))` | `subscriptionHistory` (entries with status `expired`) |
| U5 | Extension of a lapsed term: from the old end until the extension: `[before.endAt, at)` | `subscriptionEvents` (`extend`) |

**Day boundaries.** A log is refused only when its **whole calendar day, in every time zone (UTC−12 … UTC+14), lies inside one unauthorized window**: `Date.UTC(day) − 14 h ≥ window.start` and `Date.UTC(day) + 36 h ≤ window.end`. The client's time zone is unknown to the server, so a day that touches an authorized instant anywhere is accepted. Consequence: up to about a day of grace at each boundary — legitimate work is never refused for a time-zone reason.

**Refusal.** The record is returned in `rejected` with the new reason **`SUBSCRIPTION_READ_ONLY`**. The rest of the batch applies. On the device the record stays dirty (never deleted), is retried on every sync pass, and the sync detail says why. It is accepted automatically once the coach extends or renews over that date (U1 / U4 shrink); nothing else has to happen.

**What the stored data cannot prove (not enforced — reported to the owner, not guessed):**
- Terms that were overwritten **before B0** (renewals did not keep history before CO-15, which is not deployed): a log dated before the earliest known term of a relationship cannot be classified, so it is accepted.
- Freezes stored **before B3.0.1** (no `freezeCredit`, no event): their real start is unknown (the old rule froze "from acceptance", which is not recorded), so they are not enforced by the sync rule; the app still blocks logging in the UI.
- Cancellations kept only in `subscriptionHistory` (the archive has no `cancelledAt`).
- Gaps inside a relationship whose earlier stint was overwritten by a re-assignment (B3-S13).
- **Client-generated dates.** The activity date is written by the device. The rule refuses records **dated** outside authorized time; it cannot prove **when** an activity really happened. A device can back-date a log into an authorized period. No anti-back-dating guarantee is claimed; one would need trustworthy server-side evidence (for example a server-stamped start time), which does not exist today.

**Compatibility.**
- `RejectReason` gains `SUBSCRIPTION_READ_ONLY` (additive; the client mirror in `src/data/sync/contract.ts` is updated).
- B1+ clients already keep rejected records and show "Sync failed"; B3.0.1 adds a readable explanation in the sync detail (Settings).
- RC2 clients (production today) show a generic sync failure for the same records and keep them dirty.
- No data is rewritten; no collection is migrated.

**Tests:**
- pure rule tests for U1–U5, the day-boundary grace, lifetimes and "not enforced" cases;
- api `sync` tests: offline-after-expiry log refused and kept, in-term log pushed after expiry accepted, pre-term and pre-relationship logs accepted, renewal gap (incl. back-dated renewal), scheduled freeze (before / inside / after), extension of a lapsed term, other collections untouched, `pending` / no coach untouched, retry accepted after an extension;
- client: the reason is remembered and explained (`syncTruth` / contract tests).

## 9. B3-S14 — Conversation ownership after a transfer (R-4 = Option C)

**Owner decision.** Each coach may access only the messages of **their own conversation** with the client, and only while their relationship is active. A newly assigned coach must not see the previous coach's messages, attachments, previews, unread counts or message metadata. The client keeps the earlier coach conversations in a **clearly separated, read-only history**. A former coach loses thread access when the relationship ends. Legacy messages without a reliable `coachId` are **not exposed to a coach by default**. Enforced on the server — never by client-side filtering only.

**Conversation key.** A message belongs to the conversation `coachId` stored on it (`send` has written it since the move to Mongo: the coach's own id for a coach, the client's current coach for a client or admin).

| Procedure | Coach (active relationship) | Client | Admin `clients.writeAll` |
|---|---|---|---|
| `list` (incl. `since` / `before` paging) | only `coachId == me`, plus legacy messages **they sent themselves** (`coachId` missing and `fromUserId == me`) | every message of their thread (current + earlier conversations + legacy) | every message |
| `send` | written with `coachId = me` | written to the **current** coach's conversation. Optional input `coachId` (the conversation the message was composed in): if it is not the current coach → `CONFLICT` `CONVERSATION_CLOSED`. No active coach → `CONFLICT` `NO_ACTIVE_COACH` | current coach's conversation (or none) |
| `edit` / `delete` (sender, 2 min) | a message outside their conversation → `NOT_FOUND` | only inside the current conversation; earlier conversations are read-only → `FORBIDDEN` `CONVERSATION_CLOSED` | unchanged |
| `react` | outside their conversation → `NOT_FOUND` | current conversation only → `CONVERSATION_CLOSED` | unchanged |
| `markRead` | marks only their own conversation's incoming messages; clears only their own message notifications | marks the whole thread | unchanged |
| `coachThreadsSummary` | last message and unread count from their own conversation only | — | for the coach asked about |
| Message notifications (`message_received` and every coach-bound notification) | stored with the recipient `coachId`; the coach feed shows only their own, plus legacy rows created during their current relationship | unchanged | — |
| Attachment upload (`/api/media`, `message`) | thread access (unchanged) | requires an active coach; an upload bound to a closed conversation (`coachId` meta) is refused (permanent `forbidden`) | unchanged |
| Broadcast | client-side fan-out of `send` → covered | — | — |

**Durable outbox.** A queued client message carries the conversation it was composed in (`coachId` in the payload, sent to `send`). After a transfer the retry is refused with `CONVERSATION_CLOSED` (a permanent failure, kept in the outbox with Retry / Delete and a readable reason) — it can never be delivered to the newly assigned coach. Coach-side retries after the relationship ended are refused by thread access.

**Legacy messages (no `coachId`).**
- **Coach:** hidden, except the messages the coach sent themselves (their author is certain).
- **Client:** shown in the earlier-conversations history (read-only).
- **Admin (`clients.writeAll`):** shown (the documented fallback for support and disputes).
- Nothing is rewritten. A back-fill of `coachId` for legacy data would be a separate, explicit owner action with its own review.

**Client UI (functional, minimal).** In the client's chat, messages that are not part of the current coach's conversation are grouped above it under "Earlier conversations · read-only" (collapsed by default), with no reactions, edit or delete. A client with no coach sees their earlier conversations read-only under the existing "no coach" state, with no composer.

**Tests (api):** transfer (A → B: B sees none of A's messages, previews, unread counts or notifications; A loses access; the client sees both, separated by `coachId`), suspension (read yes, write no), legacy messages (hidden from coaches except their own; visible to the client and admin), unauthorized access (`NOT_FOUND` / `FORBIDDEN` without content), outbox retry bound to A refused after the transfer, upload binding.
